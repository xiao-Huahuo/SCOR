# v01 间隔式检查点策略

日期：2026-10-10（Asia/Shanghai）。这是存储与恢复策略修订，保留原生奖励、GRPO loss 和 optimizer 更新规则；旧运行与其失败状态不改写。

本文件描述已实现的3B工程试跑策略。新的v01自有baseline设计见 [baseline_design.md](baseline_design.md)：新模型须实测空间预算，step0与晚期分叉协议尚待实现，不能直接复用本文件的3B固定空间门槛。

## 保存规则

- 完整快照按 `trainer.save_freq` 的 global step 间隔保存。v01 两步试跑默认间隔为2，因此正常跑到step2只保存一份。
- 原生最后一步始终保存；主动 `--stop-after` 和显式指定的关键训练步也强制保存，即使不落在间隔点上。
- 其他步骤继续保存原始generation、真正进入updater的batch、reward、指标和计算完成收据。完整模型状态的提交边界由 `raw/durable_checkpoint_step_*.json` 与完整checkpoint证书标识。
- `--no-new-checkpoint` 仍只用于诊断，最终模型不持久化。它不能与要求实际保存的关键步选项合用。

## 配置

在服务器本项目工作目录，使用同一完整模型路径、新的run_id：

```bash
python solutions/v01/src/run_pilot.py --run-id interval_trial --model-path <模型路径> --gpus 4,5,6,7 --checkpoint-interval 2
```

可选参数：

| 参数 | 含义 |
|---|---|
| `--checkpoint-interval N` | 每N个global step保存，末步和关键点额外保存 |
| `--checkpoint-keep N` | 保留本轮最近N份完整快照及保护点；默认不自动清理 |
| `--checkpoint-pin-step S` | 强制保存并保留已完成训练步S，可以重复指定 |
| `--stop-after S` | 在S步完整记录和保存后主动停止；诊断模式不保存模型 |

每次尝试的策略和实际计划保存步写入不可覆盖的 `manifest.json`。后续Gate中需要保留的分支/审计状态必须明确保护，不能仅依靠滚动保留最近N份。当前已完成的step1快照属于旧run，新的保留策略不会清理它。

## 清理与磁盘预算

上游FSDP的 `max_actor_ckpt_to_keep` 会在新快照写入前删除旧actor目录，因此本入口保持它为None。项目策略在新快照的model/optimizer/extra、dataloader、driver RNG和证书完整并fsync后，才清理当前run中同签名、未保护的旧完整快照。部分写入、其他签名、外部目录链接和其他run不清理；原始轨迹及指标保留。

预算按实际间隔、恢复起点、末步、主动停止点和保护点计算。开启滚动清理时，新旧快照需要短暂共存；保留一份不等于磁盘只需容纳一份。

估算每份完整3B快照为BF16模型文件大小的6.5倍，并为每次写入预留至少55GiB可用空间。一次只产生一份快照需要55GiB；持续替换、保留最近一份时，峰值至少容纳旧份和新份，所需空间约100GiB，实际以启动预算为准。

目前实际单份快照约43.1GiB、余盘约32.8GiB，间隔保存不能让一份新快照放进现有剩余空间。四卡资源和存储未满足时预检停止。

## 恢复与验收边界

间隔内的已计算步骤具有原始收据，但其模型状态尚未提交。中断后从最近完整快照恢复，已提交阶段不重做；后续未提交区间可能需要重算。新的尝试使用新run_id，保留旧异常现场，不覆盖已有收据，不重复汇总两个尝试中的同一实验单元。

保存频率与保留规则不改变学习方法。原 `scor_hooks.py` 字节保持不变；服务器已实际计算新入口的训练签名，确认仍匹配旧step1快照的 `0a0fd00185a624189484f29955052fafb645c4671cfdbe2f15d0320b8048a720`。驱动新增独立检查点策略hook，其源码哈希记录在新运行manifest中。

CPU验收覆盖保存步规划、替换峰值预算、失败新写入保留旧快照、关键点保留、部分快照拒绝、外部链接保护，以及非间隔主动停止点先保存后退出。生命周期测试使用模拟小分片，不能代表真实四卡FSDP大快照验收。新策略的真实GPU间隔保存/恢复测试尚未执行；旧策略下的原生保存和恢复证据保持原样。vLLM采样RNG逐位恢复仍未验证。
